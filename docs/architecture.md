# 架构概览

本文描述 ShotForward 当前稳定的组件边界。具体数据表、接口字段与实现细节以代码和测试为准。

## 设计目标

- 本地项目是创作事实的唯一来源。
- Web、桌面与自动化入口共享同一套业务规则。
- 每次生成都能追溯输入、Provider、状态和输出版本。
- Agent 可以协作，但不能绕过用户确认和领域约束。
- Provider 可替换，工程数据不依赖单一模型服务。

## 组件关系

```text
Tauri desktop shell
        │ starts / discovers
        ▼
React Web UI ── localhost HTTP + SSE ──► shotforwardd
                                             │
                 ┌───────────────────────────┼──────────────────────────┐
                 ▼                           ▼                          ▼
          Application / Domain        SQLite + media             Runtime adapters
                 │                                                ├─ Codex / MCP
                 └─ jobs, changesets, export                      ├─ Providers
                                                                  └─ FFmpeg
```

### Desktop

Tauri 壳负责窗口、daemon 生命周期、原生选择器、安装与更新。它不包含另一套业务逻辑，也不直接修改项目数据库。

### Web

React UI 负责展示远端快照、收集草稿和发起命令。TanStack Query 管理服务端状态，SSE 用于任务与会话事件通知。前端不持有 Provider 密钥，也不直接访问项目文件。

### Daemon

`shotforwardd` 是应用核心，拥有：

- 项目、剧集、剧本、资产、故事板和媒体版本规则；
- SQLite 事务、文件导入、任务调度和失败恢复；
- Agent 会话、ChangeSet、Provider 与导出适配；
- 本机 HTTP API、鉴权、输入校验和审计信息。

## 数据布局

应用级数据库保存项目索引、Provider 配置元数据和本机设置。每个项目目录独立保存工程数据库与媒体，便于备份和迁移。

```text
application-data/
└── studio.db

project-root/
├── project.db
├── media/
├── imports/
├── exports/
└── .shotforward/
    └── staging/
```

凭据不写入这些数据库；仅保存系统安全存储中的引用或非敏感配置。

## 写入模型

普通界面操作通过命令式 API 进入应用层，在事务内验证不变量并写入数据库。长耗时操作创建持久化任务，记录输入快照、进度、失败类型和重试信息，再由后台执行器处理。

Agent 修改采用两阶段流程：

1. Agent 读取受限的项目上下文并提出 ChangeSet。
2. 用户预览差异；daemon 在应用时重新检查版本和领域约束。

这样可以避免模型直接写数据库，也能在项目已变化时阻止陈旧修改覆盖新内容。

## 生成与恢复

图片、视频和导出均以任务运行。Provider 返回的外部标识与状态会被持久化，进程重启后可以继续轮询、重试或给出明确失败原因。媒体先写入 staging，校验成功后再原子化进入项目目录并创建版本记录。

### Agent 上下文与多轮图片

Agent 输入框的文件选择和粘贴图片共用上传流程：每张最多 25 MiB，每条消息最多 5 张，上传完成前不能发送。粘贴只读取用户粘贴事件提供的图片文件，不读取剪贴板中的远程链接；普通文本和混合图文的文本部分继续使用原生粘贴。图片导入依据有界 staging 副本的真实 PNG/JPEG/WebP 内容识别格式、校验解码并规范内部后缀和 MIME，保留原始显示文件名与源文件；未要求裁剪/缩放时不重编码原图。严格解码另设 64 Mi 像素安全上限，避免小文件解压成无界像素内存。格式不支持、文件损坏、读取失败和超限分别返回可诊断的错误码，界面按语言显示说明，日志记录请求编号和失败阶段。

模型上下文由 Codex Runtime 管理，继续使用 Runtime 的模型默认自动压缩策略，不在 HTTP 代理中删除图片或改写历史 JSON。会话菜单的“整理上下文”调用原生 `thread/compact/start`，等待对应的原生 Turn 结束才显示成功；它不创建用户消息，也不删除应用聊天记录。整理期间同一会话不能发送、排队或重复整理；即使 HTTP 等待取消，也要等原生任务真正结束后才恢复发送。整理可能消耗当前服务的 Agent 额度，并非无损的长期记忆：需要图片细节时可以再次引用原素材。

发送给 Agent 的 JPEG/PNG 使用独立、按内容寻址的看图缓存（最长边 2048、编码体积不超过 1 MiB）。原图不覆盖，素材绑定和图片/视频生成仍使用原始素材；WebP 保持原路径交给 Runtime 解码。缓存目录位于各 Runtime 工作目录的 `.agent-image-inputs-v1`，会话恢复仍依赖这些文件，不应在使用中的会话下手动清理。旧会话中的图片不会自动重写成新副本。

云代理原样转发有界正文（最多 64 MiB，包括编码后的压缩正文），超限明确返回 413，不再静默截断成无效 JSON；支持原生 `/responses/compact`，保留上游错误且不自动重放用户请求。JSONL 同样有 64 MiB 消息边界。恢复会话只读取 metadata 和分页 Turn 状态；界面历史逐个 Turn 读取并聚合显示，避免多轮图片组成一条超大协议响应（Runtime 的 summary 视图也内联原图，不能解决此问题）。旧异常素材、WebP 或同一 Turn 多次带图追加仍可能触及单消息边界；不承诺无限图片历史。模型真正使用的上下文与界面聊天历史是不同的边界，仍需区分 Runtime/网关不支持压缩、上游限额与网络故障，不能用新建会话或删历史来伪装成功。

Agent `/responses` 和 `/responses/compact` 使用独立的长请求 HTTP Client，复用普通客户端的代理、TLS 和认证边界，但不继承普通请求的 90 秒总时限。连接与响应头等待最多 5 分钟；收到响应头后，连续 5 分钟未收到任何正文数据才按读取空闲超时取消，SSE 心跳字节也会刷新空闲时限。下游单次写入或 Flush 阻塞同样最多等待 5 分钟，用户取消可提前解除等待。普通账户、模型和媒体请求的原有超时保持不变。用户取消会传递到上游；流式读写异常记录安全原因并中止不完整响应，不补造成功、不自动重放。内置 Runtime 的 `error` 通知若带 `willRetry=true`，只发布当前 Turn 的非终态 `turn.retrying` 事件，不修改数据库终态，也不转发原始错误或凭据。界面按当前会话和 Turn 显示重试提示与实际已耗时；恢复输出或任务结束后清除提示，以最新 snapshot 的终态为准，避免过期历史把已结束任务继续显示为运行中。

## 本地 HTTP 安全

daemon 仅绑定回环地址。初次启动使用短期配对码交换受保护会话 Cookie；写请求同时接受 Origin 与 CSRF 校验。媒体和文件路径经过规范化，且必须落在允许的根目录内。

## 依赖方向

依赖始终指向领域核心：

```text
HTTP / jobs / providers / persistence
                 │
                 ▼
          application services
                 │
                 ▼
               domain
```

领域层不依赖 HTTP、SQLite、模型 SDK 或桌面运行时。新增能力应复用这一边界，而不是在界面、Provider 或脚本中复制业务规则。
